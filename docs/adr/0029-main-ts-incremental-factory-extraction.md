# decision-29: main.ts の分割は状態所有を残した純関数 + 依存注入ファクトリ抽出で段階実施する

## Context

`src/main.ts` は 2026-07-30 時点で実測 3,569 行（TASK-116 起票時の 2,737 行
から約 830 行増加。肥大は現在進行形）。`src/` の次点 `powers.ts`（583 行）の
約 6 倍で、対応する `main_test.ts` が無く、モジュール変数を直接読む
builder・イベントハンドラ・DOM 配線はユニットテスト不能である。責務の
実測内訳は `docs/main-ts-inventory.md`（TASK-116 の成果物）にある: レイヤー
構築 954 行（27%）・DOM UI 522 行（15%）・デバッグフック 438 行（12%）で
過半を占め、配線そのもの（renderLayers・起動・年代切替）は約 700 行に
とどまる。

本分割の目的は**並列度ではなく保守性**（テスト容易性・可読性）である。
反実仮想シミュレーションで並列度への効果が小さいことは確認済みで、
`area:src-main` の衝突ルール（docs/development-style.md 4.2 章）は分割後も
維持する。

## Decision

**状態の所有は main.ts に残し、抽出モジュールは「純関数 + 依存注入
ファクトリ」で受ける。7 単位（U1〜U7）に分け、リスクの小さい順に
1 タスク = 1 PR で段階実施する**（TASK-103 → TASK-104〜107 と同じ進め方。
後続タスクは TASK-144〜150）。

- 抽出単位と実施順: (1) デバッグフック → (2) データローダ → (3) DOM
  パネル配線 → (4) 地物レイヤー builder 群 → (5) 政治レイヤー builder 群
  → (6) picking イベント処理 → (7) 概略境界の MapLibre 同期。
- main.ts に残す配線責務（`docs/main-ts-inventory.md` §3 に定義）:
  renderLayers（レイヤー統合・描画順導出・整合検証）・yearSwitcher と
  起動シーケンス・モジュール状態の所有（選択/ホバー・データストア・
  currentView）・deck.gl オーバーレイと MapLibre Map の生成。
- 抽出モジュールは module-scope の可変状態を持たず、`createXxx(deps)`
  ファクトリまたは context 引数の純関数として main.ts から状態を注入される。

却下案:
- **AppState ストア一括導入**: 1 PR に書き換えが集中しレビュー不能。
- **レイヤー自己完結コンポーネント化**: renderLayers が担うレイヤー横断の
  整合検証（描画順 = picking 優先順など）と衝突する。
- **分割しない**: 直近の増加傾向（約半年で +30%）を放置することになる。

## Consequences

- 抽出後の各モジュールは deno test の対象にでき、main.ts は約 1,000〜1,200
  行の「組み立て図」に収束する見込み。
- 後続 7 タスクはすべて `area:src-main` を持ち**直列実行**になる（集合判定で
  他の src-main タスクと衝突扱い。並列度は目的でないため許容する）。第 2 の
  area ラベルは抽出先モジュールを示す情報として付与する。
- 抽出で壊してはならない不変条件を各タスクの AC で担保する: デバッグフック名
  （ヘッドレス検証の契約）・データローダの縮退契約（warn 文言含む）・
  メモ化の参照同値（TASK-50 / TASK-136 のホバー非再計算）。
- 新レイヤー追加時に main.ts（renderLayers・配線）へ触る構造は変わらない。
  `area:src-main` の運用も変わらない。
