# decision-31: タスク管理を backlog.md から GitHub Issue へ移行する

## Context

自律ループ（agent-loop）と人間の intake/調査セッションが別 worktree
で並行してタスク状態を書く運用になった。git 管理の `backlog/tasks/*.md`
はブランチ・worktree に閉じるため、マージされるまで他 worktree
から起票・状態変更が見えない。この可視性遅延の間は、bug 最優先ルール・`In
Progress` 一意性・重複起票検出という運用ルールの前提（全参加者が同一のタスク
状態を見ていること）が保証できない。

タスク状態は「今この瞬間の合意」であり、コードのようにブランチで分岐・収束
させる性質のものではない。ブランチフローの外にある単一ストアが必要になった。

## Decision

タスク状態の単一ストアを GitHub Issue へ移す。移行は次のシリーズで段階実施し、
本 ADR はその起点である。

1. 移行決定の ADR 化と decisions の `docs/adr/` 移設（本 ADR・TASK-137）
2. GitHub Issue 側の受け皿準備（ラベル・テンプレート）
3. タスク取得の TaskSource 抽象化
4. 起票の Issue 切替
5. agent-loop の Issue 駆動への書き換え
6. backlog.md の撤去

あわせて、backlog CLI 管理だった decisions（decision-1〜30）は `docs/adr/`
直管理へ移設した。以後の設計判断は backlog CLI を使わず `docs/adr/`
に連番の ADR として直接記録する。

## 検討した代替案

- **backlog.md 継続 + tasks の共有実体化**（`backlog/tasks/` を全 worktree
  から見える単一実体にする）: 不採用。共有実体はブランチ切替・worktree
  分離の前提と衝突し、checkout やマージのたびに状態が巻き戻る・壊れる
  リスクがある。git 管理のままではコミット・マージを介した可視性遅延という
  根本原因が解消しない。
- **専用ブランチ + 自前薄 CLI**（タスク状態だけを専用ブランチに置き、
  読み書きする薄い CLI を自作する）: 不採用。単一ストアは実現できるが、
  並行書き込みの排他制御・競合解決・履歴管理を自前 CLI
  に作り込む必要があり、GitHub Issue が既に提供する機能の再発明になる。
  保守コストに見合う独自価値がない。
- **ハイブリッド**（Issue はタイトル+状態のみ持ち、詳細本文は repo 内 md
  に残す）: 不採用。状態と本文の 2 ストア間の同期問題が新たに生まれ、
  本文側は依然としてブランチフロー内に残るため可視性遅延が本文について
  解消しない。整合を保つ仕組みのコストが単一ストア化の利点を食い潰す。

## Consequences

- 起票・状態変更が全 worktree・全セッションから即時に見える単一ストアに
  なり、bug 最優先・`In Progress` 一意性・重複起票検出をマージ待ちなしで
  判定できる。
- 受容したトレードオフ:
  - オフラインでの起票・状態変更はできなくなる（本プロジェクトの運用は
    常時オンライン前提であり、無視してよいと判断した）。
  - タスク本文の git 履歴（backlog/tasks/*.md の変更履歴）は移行後の
    新規タスクについて失われる（許容する）。
- 将来課題: タスク本文の履歴が運用上必要になった場合は、着手時と
  finalization 時に Issue 本文のスナップショットをタスクブランチへ
  コミットする「鏡方式」で補う（現時点では導入しない）。
- decisions は本 ADR をもって backlog CLI 管理を終了し、`docs/adr/`
  で直接管理する（採番規約は `docs/adr/README.md` を参照）。
