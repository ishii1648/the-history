## 1. 判定基準

すべて `scripts/audit-rivers.ts` の定数として定義し、値の根拠を実測で裏づける。

| 基準             | 定数                      | 値      | 内容                                                                                                           |
| ---------------- | ------------------------- | ------- | -------------------------------------------------------------------------------------------------------------- |
| 成分分断         | `PART_JOIN_TOLERANCE_KM`  | 1.0 km  | 正準名ごとにパートを接続距離で連結し、連結成分が 2 個以上なら「途切れ」                                        |
| 出口到達         | `OUTLET_TOLERANCE_KM`     | 2.0 km  | 河川の頂点が水域（海岸線・湖岸）／他河川／`EUROPE_BBOX` 辺のいずれにも 2 km 以内に到達しなければ「行き止まり」 |
| bbox 辺接触      | `BBOX_EDGE_EPS_DEG`       | 2e-5 度 | 出力座標の丸め（5 桁 ≒ 1 m）の 2 倍。クリップ由来の端点は -25 / 34 / 60 / 72 が誤差 0 で出る                   |
| パイプライン差分 | `PIPELINE_BBOX_DELTA_DEG` | 0.01 度 | simplify 前（フィルタ + クリップ直後）と生成物で、パート数・連結成分数・bbox のいずれかが変われば生成側起因    |

### 1.1 接続距離は「端点↔相手ライン」で測る

河川網では分流が本流の**途中**から分岐するため、端点同士の距離で連結性を判定すると
分流が誤って「分断」になる。実測でも Volga 下流の分流は本流ラインから 0.56 km の
位置で分岐しており、端点距離では 93.2 km 離れて見える。よって接続距離は
「一方の端点から他方のポリラインへの最短距離」（`partDistanceKm`）を使う。

### 1.2 閾値 1.0 km の根拠（感度分析）

許容差を掃引した全河川の連結成分数の合計（最小値は河川数の 30）:

| 許容差 km  | 0.01 | 0.05 | 0.1 | 0.25 | 0.5 | 1  | 2  | 5  | 10 | 25 | 50 |
| ---------- | ---- | ---- | --- | ---- | --- | -- | -- | -- | -- | -- | -- |
| 成分数合計 | 46   | 38   | 36  | 34   | 32  | 30 | 30 | 30 | 30 | 30 | 30 |

1 km 以上 50 km 以下のどの値でも結果は変わらない（平坦域）。0.5 km 以下では
Natural Earth の別 feature 間のノード揺れ（実測最大 0.83 km: Donau→Donau、 Elbe
のパート境界 0.48 km、Volga の分流分岐 0.56 km）を分断と誤判定する。
よって平坦域の下端 1.0 km を採る。**閾値を 2
桁動かしても判定が変わらない**ため、 値の選び方に結論は依存しない。

### 1.3 河口到達の判定方法と、採用しなかった基準

「河口に到達しているか」は**水域（`ne_50m_coastline` + `ne_50m_lakes`）への
点↔線分距離が 2 km 以内か**で判定する。頂点間距離ではなく線分距離を使うのは、
50m 海岸線の頂点間隔が数 km あるため頂点距離では到達済みでも大きな値が出るため。

**採用しなかった補助基準**: 「終端から開放海域（海岸線から 5 km 以上離れた
外洋ポリゴン内）までの距離」。エルベ型（実際の河口より内陸で終わる）を切り出せる
かを検証したが、実測値が連続分布で閾値を置けない:

| 河川                                     | 開放海域まで km | 河口まで描けているか（目視の期待）                       |
| ---------------------------------------- | --------------- | -------------------------------------------------------- |
| Elbe                                     | 72.3            | 届いていない（TASK-75）                                  |
| Tejo                                     | 62.8            | 届いている扱いだった（実際はテージョ川河口湾の奥で終端） |
| Dnipro                                   | 39.3            | 届いている扱い                                           |
| Loire                                    | 35.6            | 届いていない（ナント付近）                               |
| Seine                                    | 27.8            | 届いている扱い                                           |
| Oder                                     | 20.0            | 届いていない（シュチェチン潟）                           |
| Neva / Severnaya Dvina                   | 12.4            | 届いている扱い                                           |
| Daugava / Ural / Volga / Lek / Waal      | 7.9             | 届いている扱い                                           |
| Vistula / Ebro / Pechora / Bratul 各分流 | 5.6             | 届いている扱い                                           |

「届いている」とされてきた Tejo（62.8 km）が Elbe（72.3 km）に次ぐ値になるなど
順序が期待と一致せず、どこに線を引いても恣意的になる。よって判定基準には採用せず、
参考値としてレポートに出力するにとどめる（§3.2 の結論の根拠でもある）。

## 3. 途切れの分類と起票判断

### 3.1 (a) EUROPE_BBOX による意図的クリップ — 3 件・起票不要

| 河川      | ソース bbox                    | 出力 bbox                      | 切断辺 |
| --------- | ------------------------------ | ------------------------------ | ------ |
| Amu Darya | 58.316, 36.950, 68.212, 44.426 | 58.316, 42.272, 60.000, 44.426 | 東 60E |
| Euphrates | 37.848, 30.902, 47.468, 40.180 | 37.848, 34.000, 42.510, 40.180 | 南 34N |
| Tigris    | 39.643, 30.999, 47.441, 38.416 | 39.643, 34.000, 44.360, 38.416 | 南 34N |

**起票不要**。切断位置は
`EUROPE_BBOX`（`scripts/build-data.ts`）の辺そのもので、
`MAP_MAX_BOUNDS`（`src/config.ts`）が同値（同値性は `src/config_test.ts`
が担保）の
ため、切断点は地図の可動域の外縁と一致する。ユーザは切断面をパンで視野に入れられず、
途切れとして知覚できない。域外まで描くことは「ヨーロッパ域内」というアプリの
スコープ（`docs/data-inventory/README.md` §2）にも反する。

なお Euphrates の出力東端 42.510 と Tigris の 44.360 は自然な終端ではなく、 南辺
34N での切断に伴う端点である（両河川とも 34N より南で東へ向かう）。
これも同じ理由で仕様どおり。

### 3.2 (b) Natural Earth ソース由来 — 「河口部を海として扱う」仕様・個別起票不要

エルベ川（TASK-75）と同様に、実際の河口より内陸で終端して見える河川は
Loire（ナント付近 -1.743E）・Oder（シュチェチン潟 14.584E）・Tejo（-8.792E）・
Dnipro（32.578E）など複数ある。しかし**これらの終端はいずれも `ne_50m_coastline`
に接している**（点↔線分距離 0.00〜0.01 km）。すなわち Natural Earth
では「幅の広い河口部・潟・入り江は河川ではなく海（coastline の
内側）としてモデル化する」のが一貫した仕様であり、エルベ固有の欠落ではない。
§1.3 のとおり「実際の河口までの距離」に相当する指標では河口到達済みとされてきた
河川（Tejo 62.8 km 等）と分離できず、個別の欠陥として切り出せない。

TASK-75 の手順（10m 版での補完可否実測）を代表 2 件に適用した結果も同じ結論:

| 河川  | 50m 版の終端     | `ne_10m_rivers_lake_centerlines` の終端 | `ne_10m_rivers_europe`                      |
| ----- | ---------------- | --------------------------------------- | ------------------------------------------- |
| Oder  | 14.5835, 53.6393 | 14.5959, 53.5982（50m より南＝手前）    | 河口部に feature 無し（17.19〜18.23E のみ） |
| Loire | -1.7425, 47.2160 | -1.7345, 47.2108（50m より東＝手前）    | feature 無し                                |

（参考: Elbe は 50m 9.784E に対し 10m 9.819E で手前。TASK-75 実測）

10m 版はいずれも 50m 版より**手前**で終わっており、補完に使えるソースは無い。
decision-14（出典なき座標合成はしない・補完不能なら known-limitations で明示）に
従い、**個別河川の修正タスクは起票しない**。

**起票推奨（1 件・低優先）**: `data/known-limitations.json` の
`rivers-elbe-estuary-missing` はエルベ固有の制約として書かれているが、実際には
Natural Earth 全体の仕様であり Loire・Oder・Tejo・Dnipro
等にも同様に当てはまる。
文言を「幅の広い河口部・潟は海として扱われるため、河川ラインは河口の手前で
終わる（エルベ・ロワール・オーデル等）」へ一般化する編集タスクを推奨する。
表示上の挙動は変わらず、記述の正確さのみの改善なので優先度は低い。

### 3.3 (b) ソース側の空ジオメトリ feature（Loire）— 起票不要・記録のみ

`ne_50m_rivers_lake_centerlines` には `name="Loire"` / `scalerank=5` で
`coordinates` が空の feature が 1 件存在し、`clipRiversToBbox` →
`cleanLineGeometry` で落ちている。ただしもう 1 件の Loire feature が
上流（4.190E ローヌ・アルプ側）から河口（-1.743E）までを 2 パート（接続距離 0.05
km）で連続して覆っており、**この空 feature によって失われている区間は無い**
（成分分断 0・出口到達済み）。パイプラインの挙動（空ジオメトリの除去）も正しい。
よって起票不要とし、ソース更新時の再確認材料としてここに記録する。

### 3.4 (c) 生成パイプライン起因 — 0 件

simplify 前（`filterMajorRivers` + `clipRiversToBbox` 直後）と生成物を
河川ごとに突き合わせた結果、パート数・連結成分数・bbox 4 辺のいずれにも
有意差（0.01 度超）は無かった。`shrinkToLimit` の simplify
は端点を保存しており、 連続性を壊していない。**起票不要**。

### 3.5 検討したが「途切れではない」と判定した事象

| 事象                                                      | 実測                                                              | 判定                                                                                                        |
| --------------------------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Volga が 2 成分に見える                                   | 下流の分流が本流ラインから 0.56 km で分岐（端点距離では 93.2 km） | 分流の分岐であり途切れではない。§1.1 の基準で単一成分                                                       |
| Amu Darya の内陸終端（59.541, 44.148）                    | 水域まで 93.2 km                                                  | アラル海の旧デルタ分流の終端で、ソースがそう描いている。本流側は 0.17 km でアラル海に到達しており出口はある |
| Danube / Rhine / Elbe などの 0.5〜0.9 km のパート境界     | 最大 0.83 km                                                      | 別 feature 由来のノード揺れ。§1.2 の感度分析どおり閾値 1.0 km で吸収                                        |
| Sukhona / Vychegda / Tajo / Borcea / Nederrijn の内陸終端 | 他河川まで 0.00 km                                                | 支流・分流の合流点。出口あり                                                                                |

## 4. 回帰テスト（AC#5）

`scripts/audit-rivers_test.ts`
に**追加した**。ソース更新（`RIVERS_SOURCE_COMMIT` の変更）や `build-rivers.ts`
の変更で新たな途切れが混入した場合に検知する。

- 回帰 1: `data/rivers.geojson` の全河川が単一の連結成分であること （許容リスト
  `KNOWN_DISCONNECTED_RIVERS` は現状**空**。新たな途切れを
  許容する場合はリスト追加と本ドキュメントへの理由記載をセットで行う）
- 回帰 2: `EUROPE_BBOX` の辺で切断される河川が既知の 3 件 （Amu Darya=east /
  Euphrates=south / Tigris=south）から変化しないこと
- 回帰 3: 検査ロジック自体の空振り防止。意図的に 100 km 以上分断した
  FeatureCollection を与えて、途切れとして検出されることを固定する

回帰 1・2 は生成物 `data/rivers.geojson`
を実際に読んで検証するため、テスト実行に `--allow-read=data`
を追加した（`deno.json` の `test` / `test:watch` タスクと
`.github/workflows/ci.yml`）。ネットワークは許可しないままなので、CI
がオフラインで 決定的に動く性質は維持している。

**水域到達・開放海域距離の検査は回帰テストに含めない**。判定に
`ne_50m_coastline` / `ne_50m_lakes` / `ne_50m_ocean` の取得が必要で、CI を
ネットワーク非依存に保つ方針（`scripts/build-rivers_test.ts` の
`SOURCE_RIVER_NAMES` スナップショットと同じ考え方）と両立しないため。 これらは
`deno task audit-rivers` の手動実行で確認する。
