## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
## 背景

調査（`.outputs/claude/agent-loop-parallelism-investigation.md`）で、`deno task next-tasks` が
並列集合（2 件以上）を返したのは判定機会 32 回中 6 回（19%）にとどまることが分かった。

最大の要因は area 判定ではなく**候補の供給不足**である。`next_tasks.ts` 導入（b7edd5e）以降の
main first-parent 77 コミットを再生した結果:

- 45 コミットの時点で To Do が 0 件（バックログ枯渇）
- さらに 10 回は候補が 1 件のみ

ループの消化速度に起票が追いつかず「1 件起票 → 1 件消化」のピンポンになっている。
候補が 1 件しかなければ area 判定は働かないため、どれだけラベルを整備しても並列にならない。

## 目的

マージ後動作確認や `/code-review` で見つけた問題を 1 件ずつでなく**まとめて起票する**運用に変え、
判定機会そのものを増やす。

## 対象

- `docs/development-style.md`（2 章 bug intake・4 章のループ手順）
- `.claude/skills/agent-loop/SKILL.md`（bug intake 節・手順 4）

`In Progress` が残っている間は新集合を判定しないガード（イテレーション境界）は維持する。

## Implementation Plan

<!-- SECTION:PLAN:BEGIN -->
## 背景（起票時の調査）

`.outputs/claude/agent-loop-parallelism-investigation.md` によると、
`next-tasks` が並列集合（2 件以上）を返したのは判定機会 32 回中 6 回（19%）で、
最大の要因は area 判定ではなく**候補の供給不足**。45 コミットの時点で To Do が
0 件、さらに 10 回は候補が 1 件のみだった。

## このセッションでの再現（着手時点の実測）

`/agent-loop` を 1 回実行して 10 タスクを処理した本セッションでも同じ形が出た。

- 判定機会 8 回のうち並列集合が返ったのは 2 回（25%）
- **bug を 1 件ずつ起票した**: TASK-117（TASK-105 の実装中に発見）→ 次
  イテレーションで単独処理、TASK-118（TASK-112 のマージ後確認で発見）→ 次
  イテレーションで単独処理。いずれも「1 件起票 → 1 件消化」のピンポン。

つまり起票のバッチ化は、この運用で実際に起きている問題への対処になる。

## 方針

`docs/development-style.md` と `.claude/skills/agent-loop/SKILL.md` の
bug intake の記述を「見つけたら即 1 件起票」から「**そのフェーズで見つけた
問題を全件まとめてから起票する**」へ変える。

- マージ後動作確認フェーズ（手順 4）で複数の問題を見つけたら、**次イテレーション
  開始前に全件を起票してから手順 1 に戻る**ことを手順として読み取れるようにする
  （AC #3）。
- `/code-review` の指摘を受け入れる流れも同様に、指摘を 1 件ずつでなく
  まとめて起票する形にする。
- **`In Progress` が残っている間は新集合を判定しないガード**（イテレーション
  境界）は維持する（AC #4）。バッチ起票はこのガードと矛盾しない
  （起票はイテレーションの終わりに行い、判定はその後）。
- docs と SKILL.md の記述に矛盾が無いこと（AC #2）。SKILL.md は手順、docs は
  規約と根拠、という既存の役割分担を保つ。

## 手順

1. 現行の bug intake の記述（docs 2 章・4 章と SKILL.md の bug intake 節・
   手順 4）を読み、どこが「1 件ずつ」を前提にしているかを洗い出す。
2. 両方を書き換え、相互に矛盾が無いことを確認する。
3. 起票のバッチ化が実際に判定機会を増やすことの根拠（上記の実測）を
   docs 側に残す。

## 検証エビデンス（finalization）

**AC#1（docs にバッチ起票の運用が明記）**: `docs/development-style.md` 2 章に「起票はフェーズ単位でバッチ化する」を独立の箇条書きとして規約化し、起票フォーマットに「バッチでも **1 件 = 1 タスク**。複数の問題を 1 タスクにまとめない」を追記。新設 4.2.1 章「bug 起票のバッチ化（判定機会を増やす）」に根拠（実測）・運用・イテレーション境界ガードの維持・限界の 4 ブロックを置いた。

**AC#2（SKILL.md が同じ運用に更新され docs と矛盾がない）**: SKILL.md の bug intake 節を全面改訂（見出しも `…・ユーザー報告・/code-review からの起票` へ）。矛盾の回避は 3 点で担保:

- 役割分担の維持: SKILL.md は「いつ・どこで・何を実行するか」、docs は「なぜ・規約として何が要求されるか」。SKILL.md は根拠を再掲せず docs 2 章・4.2.1 章へ参照する。
- **実測値は docs 4.2.1 章にだけ置き SKILL.md には書かない**（値の二重管理を作らない。4.4.1 章のエスカレーション上限と同じ扱い）。
- 「フェーズ単位でバッチ化する」「1 件 = 1 タスク」「次イテレーション開始前に全件」の 3 フレーズを両文書で揃え、片方だけ読んでも同じ運用に到達するようにした。

**AC#3（複数の問題を見つけた場合の手順）**: SKILL.md 手順 4 の末尾に「問題を見つけてもその場で 1 件ずつ起票しない。確認をやり切って一覧化したまま手順 5 へ」、手順 7 を「**手順 1 に戻る前に**全件起票 → 起票を終えてから手順 1 に戻る」の 2 段構成に書き換えた。

**起票地点を手順 7 にした理由**: 手順 4 直後に起票する案もあったが、集合が複数タスクの場合はタスクごとに手順 3〜5 を回すため、手順 4 で起票するとタスクごとに分散して結局バッチにならない。全タスクのマージと後始末が終わったあと、手順 1 に戻る直前が唯一バッチの成立する地点。

**AC#4（In Progress ガードの維持が docs から読み取れる）**: docs 4.2.1 章に独立段落を置き、既存 3 箇所（4.1 章のルール 4・4.2 章の「In Progress のタスクが存在する間は空集合を返す」・4.3 章の安全ガード）への参照を明示した。いずれも既存記述で今回変更していない。「起票はイテレーションの終わり、集合判定はその後」という順序で矛盾しないこと、「イテレーション途中で見つけた問題を現イテレーションへ合流させることは引き続き行わない」ことを明記。

**検証**: `deno task test` = 1262 passed / 0 failed / 3 ignored（ドキュメントのみの変更なので既存が通ることの確認）。`deno fmt --check`（149 ファイル）green、`deno lint` は既存 4 件のみ、`deno task build` green。CI（PR #122）`ci: pass`・`mergeable=MERGEABLE state=CLEAN`。

**手順番号の繰り上げは行っていない**（新規手順を足さず既存 4・7 に追記したため、「手順 5 の worktree remove」「手順 6 のエスカレーション」等の既存参照は無傷）。TASK-112 / TASK-118 が直近で入れた手順 2 の worktree 復元・手順 5 の `--force` 記述は最新版を読んだうえで一切変更していない。

## このセッション自身が症例だった

`/agent-loop` を 1 回実行して 10 タスクを処理した本セッションで、起票時の調査と同じ形が再現した。

- 判定機会 8 回のうち並列集合（2 件以上）が返ったのは 2 回
- **bug を 1 件ずつ起票した実例**: TASK-117（TASK-105 の実装中に発見）→ 次イテレーションで単独処理。TASK-118（TASK-112 のマージ後確認で発見）→ 次イテレーションで単独処理

## 限界を正直に書いた

バッチ化が判定機会を増やすのは「同じフェーズで**互いに独立した**複数の問題を見つけた場合」に限られる。**TASK-118 は TASK-112 が入れた後始末そのものが動かなかったという直接の帰結**で、TASK-112 のマージ後動作確認でしか見つけようがなく、バッチ化しても同じイテレーションには入れられなかった。この実例を docs 4.2.1 章に書き、「バッチ化は並列化の十分条件ではなく供給不足を緩和する一手段」と結論づけた。

あわせて SKILL.md に「バッチ化が効かない場合は単独起票のままでよい。無理に他フェーズの問題と束ねて起票を遅らせない」を入れ、原則を守ろうとして起票を先送りする逆効果を防いだ。

## 申し送り

`CLAUDE.md` にも同趣旨の 1 行（「動作確認で見つけた問題は label `bug` 付きタスクとして起票し」）があるが、TASK-113 の担当ファイル外なので未変更。バッチ化と矛盾はしない（「起票してから直す」はバッチでも成立する）が、明示したいなら追随の余地がある。

## decision 記録の判定

**記録しない**と判断した。バッチ起票は `docs/development-style.md` 2 章・4.2.1 章が一次情報で、decision に本体を書くと二重管理になる（development-style 2.1 章の「重複記録は同期切れ・形骸化を招くため禁止」）。既存規約（bug intake・イテレーション境界ガード・1 件 = 1 タスク）の枠内での運用の詰め方であり、方式の選択ではない。
